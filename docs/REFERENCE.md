# Loadout

Native Rust cabin. No Electron. No Tauri in the egui cabin; the cross-platform Tauri shell is planned in [`docs/cross-platform/README.md`](cross-platform/README.md). One repo, one `main`, one version — two ship artifacts.

**v3.5.0** — The Loadout look: one brand file names the app and its companion, Nyx becomes the default personality for new installs, Ops Dark, OLED Black and Soft Charcoal themes arrive, the cabin's chat home gets a dock, Pulse reflows from side-by-side to one column and can follow your Steam library's game news, and the shell gets an Activity Dock for running chats, approvals and automation runs.

|----------|----------|--------|
| **Linux** (Arch / CachyOS) | `grokhub-linux-v3.5.0.tar.gz`, AUR | **v3.5.0** |

## Run

```bash
sudo pacman -S --needed git rustup base-devel pkgconf gtk3 libxkbcommon libxkbcommon-x11 ffmpeg alsa-utils
rustup default stable
git clone https://github.com/blackviperxiii-ui/GrokHub.git
cd GrokHub
cargo test --workspace
./scripts/install.sh --user
grokhub
```

Or without installing:

```bash
cargo run -p grokhub-app
cargo run -p grokhub-app -- --agent
cargo run -p grokhub-app -- --hub
cargo run -p grokhub-app -- --doctor
GROKHUB_HUB_PORT=18766 cargo run -p grokhub-hub
```

The tray icon is there from launch. Close / titlebar × hides the cabin — the window unmaps and stays unmapped until it loses focus (then a pinned taskbar click, tray **Show cabin**, or a second `grokhub` raises it). It does not minimize to the taskbar. Drag the titlebar body to move the undecorated window. Size and position come back on the next launch. Jobs, hub, and idle reflect keep running. Tray: **Show cabin**, **Halt**, **Quit**. The first hide shows one “Still running in the tray” toast and writes `closeToTrayTipSeen` in `app.json`. Later hides, including after relaunch, do not toast. A first hide during quiet hours does not set that flag, so the next hide outside quiet hours can still tip once. The cabin status line still says it is in the tray. `grokhub --agent` starts already hidden. `GROKHUB_TRAY=0` quits on close.

Chat runs on Loadout's own native engine (`crates/grokhub-agent`), signed in with the cabin's SuperGrok device-code OAuth (`grokhub --oauth`, or Settings → **Account**). Nothing spawns the Grok Build CLI, and the cabin never reads or writes `~/.grok/auth.json`. When the permission pill is Ask, tool calls show Allow / Deny cards from the native gate. MCP elicitation (form or URL) asks in the same chat. An MCP call that isn't read-only or marked idempotent carries an `idempotency-key` in `_meta`; resending the same call within ten minutes reuses that key, and when an answer is lost mid-call the model is told the call may have run and to check first. On Windows, shell commands run PowerShell with UTF-8 in and out, and a command too long for one command line runs from a temporary script that deletes itself. On Linux and macOS a command over 128 KB is turned back with a note to put the long part in a file. MCP servers start connecting in the background when Loadout opens, side by side, so the first chat doesn't wait on them. A chat's MCP tools stay fixed for the rest of a turn; a server that connects meanwhile joins at the end of the list on the next message. Night, loops, `/send`, and `/bg` runs inherit that same PermissionMode pill. Under Ask they fail closed, because nobody is there to answer a card: the gate refuses writes, shell, and desktop tools. A side question asked while a run works gets its own read-only answer beside it, on a throwaway copy of the chat that History never lists; the run keeps going. Bound project is the workspace; unbound uses `~/GrokHub-Work` (never the cabin process cwd). `/update` updates only the cabin. `/context` and `/usage` show the native session's tokens (including reasoning); `/usage` also totals today's cabin spend. `/compact` talks to Grok. Halt stops the native turn. Truncated replies and transient 5xx retries stay on the same turn. A reply that drops after part of it showed isn't sent again: the turn stops with what showed, and that text stays in the chat's history. Stop ends a waiting reply within a second. A quiet stream counts as stalled after 120 s, or 300 s at high and xhigh effort. A 429 waits at most 30 s and the thinking line says so; calls to each model are paced under xAI's per-second limit, which halves after a 429 and recovers as calls succeed. The same tool call with the same arguments runs at most twice; a file edit resets that count. Credit-limit errors offer Try Again. Chats from the old Grok Build CLI under `~/.grok` still show in History and open read-only (`crates/grokhub-core/src/cli_history.rs`).

Slash: `/help` · `/new` · `/scratch` · `/clear` · `/undo` · `/retry` · `/stop` · `/sh` · `/host` · `/plan` · `/always-approve` · `/sessions` · `/inspect` · `/project` · `/memory` · `/recall` · `/forget` · `/board` · `/imagine` · `/skill` · `/compact` · `/learn` · `/update` · `/send` · `/sync` · `/hub` · `/inhabit` · `/rewind` · `/room` · `/export` · `/rename` · `/pin` · `/delete` · `/dream` · `/palette` · `/bg` · `/queue`. Type `/help` in the cabin for the rest. `/skill <name>` runs that skill. Skills and Connectors lists **Cabin skills** (`~/.config/GrokHub/skills`) next to **Project and user skills**, with the run count and Use in chat, plus nightly **Suggested** tiles that Add via `save_skill`. Connectors holds the GitHub PAT and read-only Who am I / List repos tiles. `/compact` keeps the last 8 visible turns and, with `/workflow`, honors the PermissionMode pill. After any compaction, the instructions you gave earlier in the chat (lines like never, always, don't, from now on) and the safety rules are re-sent word for word after the summary. Next to them goes a ledger the app keeps from the tool calls themselves, not from the summary: the files written, the last 20 commands and how each ended, and the open todos. It carries over every later compaction, on Grok, OpenRouter and the local model alike. Each new summary also keeps any earlier ask, error fix or message of yours that it dropped, while its current-state parts take the new text. Compaction starts early, in the background, once a chat passes 70% of its window (or comes within 30k tokens of the compaction line before xAI's long-context price step); the run keeps going, and at the line the finished summary is swapped in with everything since kept after it, so a run rarely stops to compact. A summary still being written there is waited for, not started again; one that no longer fits the chat is dropped and the usual compaction runs. Local models skip it, and `background = false` in `compaction.toml` turns it off. Before it compacts, the chat saves only its own words, the newest 8 KB, to session memory. `/dream` keeps a memory file as it was when a rewrite would drop over half of it or a line recall used lately, and says how many lines it kept and which it dropped. Lessons the nightly dream adds to the `dream-lessons` skill stay out of chats until a paired live eval (`--ab dream_lessons`) shows they help, and each new lesson needs a new pass. A few facts the app checks for itself go into the prompt: a project's test and build commands, read from its own files, and the GPU, read each launch. A fact its check stops agreeing with is retired, and one not re-checked in 30 days stops showing. Only the newest 3 images in a chat stay whole; once three more pile up, the older ones become a short note asking for a fresh screenshot (`keep_recent_images` in `history_trim.toml`; `age_out = false` keeps them all). Trimming and compaction go by the provider's own count of the last prompt plus an estimate of what's new, so sealed reasoning isn't counted by the size of its encrypted blob. After the first message, small talk and bare go-aheads ("ok", "lol", "do it") recall no memory. Every Grok request is sent with `store: false`, so xAI keeps no copy. `/workflow pause`, `/workflow resume`, and `/workflow stop` use that pill. Empty `/workflow` and `/workflows` open Skills on Workflows. `/context` counts visible turns. `/scratch` blocks `/forget` and Memory Save. `/rewind files` restores the bound project root. Plain `/rewind`, and `/undo` on a finished reply, say "N/A on native threads: the session is append-only." `/worktree` says there is no such command: chats run in the bound project folder, and only helpers work in worktrees of their own. `/sync` merges chats and memory with paired computers. `/project` also takes `bind`, `new`, `folder`, `rename`, `move`, `delete`, `clear`. Right-click a sidebar project to rename or remove it — Delete drops the row, not the files.

There is no mode to pick: each message is read on its own. With nothing running, a big multi-step job plans first and anything else is answered; `/plan` or `/chat` sets just the next message. While a reply runs, a side question ("btw …", or one that doesn't touch the work) is answered in an **On the side** card above the box, read-only and kept out of the chat and History; **Tell the main task** feeds it in. A correction steers the run, "stop" stops it, and a new job waits its turn. In a casual chat (small talk or a quick question, no work running) every message typed during a reply waits as its own turn and gets its own reply in the chat; a typed `/btw` still answers on the side. A side answer that fails goes in line as its own message, and a steer sent after the run last checked for one goes as its own next turn. Stop hands queued messages back one by one, never joined: the first into an empty box, the rest wait in line and go after the next reply or on "continue". "No, just answer" or "make a plan first" right after a message fixes that read and teaches it, on that computer only. **When the AI wants to change things** (Ask / Auto / Always) is one setting in Settings → Defaults, kept across launches; the permission card's **Stop asking me** moves it one step looser. On a permission card, **Enter** allows and **Esc** denies while the composer is empty; a half-typed follow-up still sends on Enter. Ask shows Allow / Deny cards from the native gate. Side answers stay read-only on Auto/Always and never stop a live run. There is no model or effort control: the router picks both on each step, and a chat question about it gets the model and effort that answered. Grok's own hosted web and X search, which the gate can't see, rides only an attended, writable chat that is online, has no deny or ask rule for search and carries no recalled memory lines; otherwise search goes through the cabin's own `web_search` tool, its rules and the send check. Hosted search runs at most 2 search rounds for a chat or a question, 3 for a task or a fix, and 5 for research (`max_turns`). Its calls go back to Grok with the next request, like its sealed reasoning, and each call's record lists the searches billed and how many pages the reply cited. Plan, btw and other read-only turns have no search, and a background digest uses hosted search only when your rules allow it.

The **Automations** page holds both schedulers. **Scheduled** is the cabin's own clock list (`automations.json`) — pause, **Run** now, or **Remove** a job, and each row shows its schedule, next run and run count. **Loops** is the cabin's interval list (`loops.json`), fed by `/loop`. **New job** takes either shape: `/loop 30m check deploy` or `every weekday at 9, summarize the board`.

The left-rail **Chat** button is the new-chat control — there is no separate New chat row. Click Chat on an empty draft (no dialogue) to pull that same chat up. After a reply has started, Chat opens a new draft. One empty draft at a time. Old convos stay in sidebar History (the cabin's own chats).

Projects sit in the left rail. `+` makes a one-level folder. It does not create a project. Double-click or right-click to rename (display name only — the path stays). Right-click a project to add it to a folder or remove it. Folders are sidebar only; they do not move files. A folder looks like a folder. Click it to show the chats underneath. That click does not open a chat, and it does not hide or replace History. A chat under the folder opens that chat only. It does not filter, hide, or remove the other chats. A project is a chat row under its folder. Clicking it opens that chat. Every chat that belongs to the folder or to a project inside it is listed under the open folder, and those chats stay out of History. Collapsing the folder hides them in the project tree and does not change History. Creating a project does not wipe History. Clicking a chat in History opens it and leaves that row where it is. A new message moves the row. Selecting, focusing, or opening a row is not activity. Pins stay last-pinned-first. Right-click a folder or project and choose New chat to file another chat there; the projects stay in the folder. Delete puts those chats back in History and does not wipe transcripts. A project click does not open the Workboard. Bound tree is the world.

History search runs as you type across SOUL/USER/MEMORY and every non-archived chat; a new query drops the previous needle's hits so a late walk cannot open the wrong thread. Archived chats leave History lists and search (still on disk; no Archived drawer) — `/recall` skips them the same way. A hit is a door — click a memory line to open that file in the editor, a chat line to open that thread. Re-opening the memory file already in the editor keeps unsaved typing. Below the search, History is the cabin's own chats (newest used, pins on top). Each chat keeps its own native session. Background runs such as “summarize the workboard” are not rows. Right-click **Delete** or the History-page Delete button removes the cabin chat and its native session. Transcripts stay on the chat until you delete it.

Labs / off-by-default agent paths: `generative_ui.toml` enables `show_panel` and inline chat panels; screen recording offers **Save as skill** after stills land (vision extract on confirm); background and unattended jobs send a lean per-job `ToolSet`. Offline technique A/B notes live under [`docs/eval/r6-technique-ab.md`](eval/r6-technique-ab.md). The switch files in the config folder (`generative_ui.toml`, `history_trim.toml`, `shell_sandbox.toml` and the rest) take `key = value` lines, and `#` starts a comment only outside quotes. A line the app can't use (a value like `flase`, a key the file doesn't have, a `[section]`) keeps the default and shows in the Settings status line and `/doctor` until the file is fixed.

Every model request is kept on this computer, sealed with the learned-tier key, for 14 days after a request last used it (`request_replay.toml`: `enabled`, `keep_days`; no key means nothing is kept). Each part of a request (the tool list, each input item) is stored once by its SHA-256, so a chat's shared prefix costs one copy, and a model-call span's route record names the request by the hash of its exact bytes. `cargo run -p grokhub-agent --example replay_request -- <hash>` prints that request byte for byte; nothing is sent. Each tool call that a rule, the Auto judge, a hook or the sandbox stopped or asked about leaves one sealed line in `safety-events.jsonl`: the tool, who decided, the person's answer and the request that produced the call, with no arguments or refusal text.

Imagine stills use dedicated **`grok-imagine-image-2.0`** (falls back to `grok-imagine-image` on timeout). Video kind calls **`grok-imagine-video-1.5`**. Auth reuses Settings → Account (Grok sign-in), then Imagine's optional OS-keychain tokens, then a console key. Hey Grok: one open mic for the voice session; a turn ends when you stop talking (or when xAI's streaming speech-to-text Smart Turn hears you've finished), with live words in the status line and the one-shot upload as the fallback. The reply is spoken sentence by sentence as it streams (thinking and command lines are never spoken), and a tap or talking over it cuts in. See `docs/compass/voice.md`. Same on Linux and Windows. Desktop control is the cabin's own `grokhub-desktop` / `grokhub-cua` MCP. The cabin keeps tool cards, diffs, and desktop frames in a collapsed Work tree in chat. No Desk / Take over menu. The shipped `grokhub-desktop` MCP is the desktop tool path on Linux and Windows. In front of it and every other tool call, the cabin runs a stricter pre-check that never loosens the permission pill: a hard floor deny, a white hard-class card even under Always (money, send, delete, credentials, irreversible OS: partitions, the bootloader and writes into `/boot` or the ESP; agent instructions and settings: writes into `.claude/`, `.grok/hooks/`, `.grok/skills/`, the cabin's own skills and memory folders, and any `AGENTS.md`, `CLAUDE.md`, `MEMORY.md` or `SKILL.md`; a lead's request to merge a helper's work). A model write to a `MEMORY.md` has secrets redacted, as `/remember` does, and is indexed for recall. Auto mode's judge never decides a hard-class step. A shell command that installs a low-level input driver such as Interception is refused outright, and one that installs a fan, RGB or monitoring tool whose driver Microsoft's vulnerable driver blocklist names gets a white card saying why anti-cheats may refuse to start with it (`driver_blocklist.json`, fetched on Windows at most once a month; with no copy yet, nothing is flagged). A workspace's `.claude/settings.json` allow rules apply only once you trust that folder; its deny and ask rules always apply, and Settings → *Let Grok control the desktop* as Access. Full is an inline Grant full card in the Work tree. With Always on, nothing else asks: `sudo`, package admin (`pacman -S`, `systemctl restart`), commands the engine can't split, and your own ask rules run without a card; deny rules and the floor still refuse. On Linux, `sudo` in those commands asks for your password once per session through a system password dialog (`kdialog`, else `zenity` / `qarma` / `yad`): agent commands run with no terminal, a `sudo` wrapper first on `PATH` that adds `-A`, and `SUDO_ASKPASS` pointing at `grokhub --askpass`, which asks the cabin over a private socket. The cabin answers only its own helper under a root `sudo`, keeps the password in memory until it closes, and never writes it to disk. A run doesn't end just because the model stops calling tools: for a task with several parts the model writes a goal checklist with `todo_write`, and while any item is open the run tells it what is left and goes on (a "continue" picks the same list up). An item marked done counts only once a real tool result exists in that run. If the model stops three times in a row with no new tool result, the run ends naming the open items as blocked. A run also knows how long its kind of task usually takes: once there is enough history, reaching the 90th percentile of the tool steps that successful runs of the same kind took (never under 12) gets the model one note to step back and finish the shortest way, and at 80% of its token budget it gets one note to wrap up before that budget pauses it. Each workspace shapes its own up-front tool list: after ten sessions there, a built-in tool outside the coding core that no session used in the last ten waits in the deferred index, and a deferred tool used in five of the last ten comes up front (three at most). The list is fixed when a session starts, every tenth session gets the full default list back, and the record (`tool_use.json`) keys workspaces by a hash, not their path. Before a turn ends, the reply is checked against the run itself: a table total or an inline sum that doesn't add up, a test or file count that doesn't match the command output, "tests pass" after a red or missing test run, and "committed", "pushed" or "updated `file`" with no step that did it each get one note back, once per turn. Runs with background or subagent work skip the step checks, since their steps aren't visible. An episode claim with a wrong sum is turned back in code without a judge call. A scan, diagnosis or review ends with a findings card after the reply (`report_findings`): findings by severity, each naming its item, and a pill per one-tap fix. A tapped fix starts a follow-up run in the same chat with that fix as its goal, through the normal gates; Dismiss hides the pills and keeps the report. Halt / Stop / tray Halt / Ctrl+Alt+H stop the native turn. Stream buffers clip at `IMAGE_FILE_CAP` / `TEXT_FILE_CAP`. Desk frames drop above `FRAME_CAP`. Titlebar × unmaps to tray. Plus-button stills ride the native turn as image input. Outside text reaches the model fenced as data: fetched pages, a shell command's output when it went through the network proxy, a subagent's result (over 12,000 characters, the rest is saved to a file it can read), and a file written after the run saw such text. Batched tool calls keep the run's fence, origin and recall lines. The pre-check reviewer sees the head and tail of a long call, with a marker where the middle was left out, and its fast path covers only the shell and monitor. It never sees the whole chat: only what you asked in your own words (your first ask and your newest four, kept across compaction), the last eight tool calls and the agent's latest words with tool results left out, and the action. A helper's reviewer also sees its brief, marked as written by the lead agent. Three replies in a row with a denied step, or six of the last twenty, end the turn with a note not to work around them. Origin checks: the run keeps the email addresses, sites and phone numbers you wrote (and recalled memory lines), and those that only outside text named. A shell command, connector tool, scheduled task or mod install that carries a value only outside text named gets a white card even under Always (`outside_value`), and an unattended run refuses it. The project's own git remote hosts count as yours; reads, browsing, file edits and the desktop are not checked. A subagent shares its parent's record, and its task text does not count as yours. A general subagent the chat starts (no persona, no worktree) is a fork: it begins with the chat's own system prompt, tools and history plus its task, under the chat's cache key, so its first request reuses the chat's cached prefix, and only its final reply comes back. A subagent it starts begins fresh. An explore subagent starts fresh with read-only tools. Routing reads the newest thing you wrote, never a note the app adds mid-run (a checkpoint, a background notice, the ledger or a summary), so those don't count as a new turn. While a Riot game is in a match (League of Legends' game client, or VALORANT or 2XKO open), an ask for gameplay advice gets one line saying Riot doesn't allow live coaching and is never sent; settings help, a look back at a match and anything else still go through. The publisher table lives in `game_profile.rs` (`MATCH_RULES`). `enabled = true` in `boundary_routing.toml` (off until a paired live eval, `--ab boundary_routing`, passes it; a pass turns it on unless you made that file yourself) holds the effort a run started with until the next turn or compaction, never under its class floor, and has a general helper start fresh on the quick lane with a brief in its prompt: Goal, Constraints, Edge cases, Done when and Files, one labeled line each. Subagents trim and compact like the chat and stop after sending about 400k tokens of their own (200k a level further down); only the chat writes its session log to memory at compaction. A sandboxed shell command can write the workspace, the temp folders and package download caches (`~/.cargo/registry`, `~/.npm/_cacache` and the like), not a tool's own folder such as `~/.cargo`, whose `bin` and config run later with no sandbox. If a sandboxed command changes the workspace's `.git/config` or `.git/hooks`, the sandbox puts them back and tells the model to rerun outside the sandbox, which asks first. The cabin's own git calls (subagent worktrees, plugin installs, updates, the code folder scan) run with hooks and fsmonitor off. On Linux, where unprivileged namespaces are allowed, a sandboxed command also gets a network of its own: its only way out is the egress proxy, so `--noproxy`, raw sockets and DNS go nowhere, while a server it starts on its own `localhost` still works. It can't open new Unix sockets (socket pairs still work) or `io_uring`, and secret folders read as empty: `~/.ssh`, `~/.gnupg`, cloud and registry credentials, browser profiles, the sign-in folder and the cabin's config folder. Git over SSH and services on the host's own `localhost` then need the command run outside the sandbox, which asks first. On macOS a sandboxed command runs under a Seatbelt profile (`sandbox-exec`) that does the same three things: its only outbound connection is the proxy's port, so DNS, raw sockets, Unix sockets and other `localhost` services are closed; it writes only the workspace, temp folders and caches (including `~/Library/Caches` and Xcode's DerivedData); and the same secret folders plus the keychain files and browser profiles under `~/Library` can't be read. A test that starts a server and connects to it needs `outside_sandbox` there, as do tools that sandbox themselves (SwiftPM's manifest step); `GROKHUB_SANDBOX_NO_SEATBELT=1` turns the profile off. On Windows 11 with the process container (24H2 build 26100.9278 or later) a sandboxed command runs in its own container through Microsoft Execution Containers, with no administrator rights: its only outbound connection is the proxy's loopback port, it writes only the workspace, temp folders and caches, and it reads system and tool folders plus the home folder without the secret folders (Windows credentials, browser profiles, cloud and CLI sign-ins); where the system can't deny single folders it reads only a short list of config folders in the home folder instead. Older Windows keeps the write-restricted token and the proxy variables, a container that fails to start switches back to the token for the rest of the session, and `GROKHUB_SANDBOX_NO_MXC=1` turns the container off. In Auto mode, an ordinary command the sandbox fully holds (writes, network and secrets: Linux with Landlock and its own network, macOS with the network guard on, or Windows in its container with the network guard on) runs without the judge or a card; hard classes, `outside_sandbox`, privilege raising, dangerous commands and your Ask rules still ask, Supervised still asks every time, and `auto_allow = false` in `shell_sandbox.toml` turns it off. `grokhub --doctor` says which of these apply on the machine. The proxy lets a sandboxed command reach only package registries, code hosts (GitHub, GitLab and the like), the model hosts and the hosts your own `WebFetch` allow rules name; your `WebFetch` deny rules win. Each host is checked by name before any DNS lookup, an IP address or `localhost` goes only when a rule names it exactly, and an allowed name that resolves to a local address is not dialed. Any other host gets a 403 and the command can be rerun outside the sandbox, which asks first. On Linux and macOS, tokens in the app's environment (`GH_TOKEN`, `NPM_TOKEN`, `XAI_API_KEY` and anything named like `*_TOKEN`, `*_API_KEY`, `*_SECRET` or `*_PASSWORD`) reach a sandboxed command only as stand-ins with the same prefix and length. The proxy puts the real value back only in request headers, only over HTTPS it ends itself with a session CA, and only for that token's own hosts: GitHub for `GH_TOKEN` and `GITHUB_TOKEN`, GitLab, the npm registry, crates.io, Hugging Face, and the xAI API. Other tunnels pass through untouched. The CA's key stays in memory, its certificate is limited to those hosts, and commands trust it through `SSL_CERT_FILE` and the like. A token with no known host is never put back, and without a system root bundle tokens stay masked and aren't put back either. Every agent command and every MCP server the app starts skips npm and PyPI releases younger than seven days (npm's `min-release-age`, uv's `exclude-newer`, pip's `uploaded-prior-to`, pipx and Poetry's cooldowns), unless the app's own environment already sets one; `days = 0` in `package_age.toml` turns it off. A plain `npm install`, `pnpm install`, `yarn install` or `uv sync` beside a lockfile gets one note pointing at the locked form (`npm ci` and the like).

Settings → **Account** is Super Grok device-code OAuth only — **Connect** / **Sign out** (or `grokhub --oauth`). Tokens live in `~/.config/GrokHub/secrets.json` (mode 0600; Windows user-only DACL), never in markdown. Settings → Appearance is **Dark**, **Light**, or **System**. Settings → Behavior holds close-to-tray, the living wall, and one **quiet hours** dropdown (Off / common windows). Picking a window saves it. Settings → **Cabin defaults** pins the chat model, reasoning effort, Ask or Auto, and Chat / Plan / btw in `app.json`, plus **Always collapse**. Auto model saves an empty pin. Always is not written from that page. Close-to-tray still hides the cabin; the desktop tip is once, and only when quiet hours allow it. GitHub PAT is not a Settings page — the connector owns that.

Windows Setup, the Linux tarball, and the AUR package install only the cabin. None of them installs, signs in, or updates the Grok Build CLI. The one place the cabin looks for the CLI is the Marketplace: when `grok` is already installed, Google's MCP connectors can point at it (`crates/grokhub-app/src/google_mcp_via_cli.rs`). The cabin never installs, runs, or updates it.

Settings → **Update** is one **Update** control (always visible), progress, and **Restart** after a clean cabin overlay. It updates only the cabin. The cabin checks every 2 hours (and at launch) for a newer GitHub Latest cabin. The titlebar chip is the notice (in-app — not a web page) and says **Update cabin**. The Settings button stays up when the probe found nothing so you can still overlay. `grokhub --update` / `/update` use that same rule. When the cabin is newer it retargets a leftover Origin or `GrokHub-Windows` clone to GitHub (`https://github.com/blackviperxiii-ui/GrokHub.git`), then `git pull --ff-only origin main` (`origin beta` on a beta install; see Channels). Linux overlays with `./scripts/install.sh --user`. Windows Setup users do not need a clone: when the cabin is newer, Update downloads the latest `grokhub-windows-v*.zip` from GitHub into `%LOCALAPPDATA%\Programs\GrokHub`. A leftover Windows clone (wrong branch, detached HEAD) uses that same zip. A Windows source clone on `main` still overlays with `scripts/install-windows.ps1`. The clone path is not a Settings field — empty uses `GROKHUB_SRC` or the install receipt. After a clean overlay, **Restart** reloads hub, drops the cabin pid lock, starts a new overlay `grokhub`, and exits this process.

Settings → **About** is the app name, version, doctor, and a redacted diagnostics copy. It does not list today's usage buckets (`/usage` still does).

Chat runs on the native engine on this desktop (full filesystem and shell; Grok is told not to claim it lacks computer access). Night, loops, and `/send` tasks enqueue the same on the bound project and inherit the composer PermissionMode pill. Halt / Stop / Ctrl+Shift+Esc stop the turn. Chat only saves a night job when you asked to schedule one — a reply that mentions “every day at” or “heartbeat every” as advice does not. A clock ask (“every weekday at 9pm, summarize the board”) is saved as a cabin automation in `automations.json` with its hour intact; an interval ask (`/loop 30m`, “every 2 hours”) is saved as a cabin loop in `loops.json`. The pulse fires both. Anticipate only fires a `Follow skill` on a real `need to` / `remind me` insight that matches a skill, not polite “if you need” chit-chat. A 15s heartbeat runs housekeep, inbox, night, review, wall, mid-thought, reflect, and anticipate. Hidden idle cabins wait for that pulse. A queued `/send` task completes on halt / error. `/rewind files` restores only the bound project root.

## Channels: stable and beta

There are two channels. **Stable** is `main`, where releases are cut. **Beta** is the `beta` branch, where new features and fixes land first. Every merge into `beta` publishes a pre-release named `v<version>-beta.<N>` with the same Linux and Windows files and `SHA256SUMS` as a release, so the beta updater can take it right away; a nightly build (about 3 AM Central, skipped when nothing new landed) backs it up.

**Without a source clone** (every Windows Setup install, and a Linux install from the release tarball), turn Settings → Labs → **Beta channel** on or off. Loadout downloads the newest beta pre-release (or the latest stable release), checks it against its `SHA256SUMS`, swaps `grokhub` and `grokhub-hub` in (keeping the old ones as `.old`), and only then saves the new channel. A download that doesn't check out leaves you on the channel you had. Update on a channel works the same way: Beta takes the newest pre-release by build time.

**From a source clone** (the developer path), switch on Linux with one command; it builds from source:

```bash
./scripts/install.sh --user --channel beta     # fetch origin, check out beta, build, install
./scripts/install.sh --user --channel stable   # back to main
grokhub --version                              # GrokHub 3.5.0-beta.3 (beta @ abc1234) or GrokHub 3.5.0 (main @ f7dcf9a)
```

`--channel` fetches `origin`, checks out the branch (creating a local tracking branch the first time, and fast-forwarding it after that), then builds and installs. Stable follows `main`, not the latest release tag, because the in-app Update already pulls `main`. The switch refuses to run over uncommitted changes, and it stops instead of resetting when your local branch has commits that aren't on `origin`.

The channel is saved to `~/.config/GrokHub/channel` (or `$GROKHUB_CONFIG/channel`), next to the `source` receipt. A plain `./scripts/install.sh --user` keeps the saved channel and builds whatever is checked out; it doesn't move git. Settings → **Update**, `/update`, and `grokhub --update` read the receipt: a beta install pulls `origin beta` and never `origin main`. If the clone isn't on the channel's branch, Update stops and says which command to run. `./scripts/install.sh --dry-run` prints the channel, branch, and receipt it would use, and exits.

`--version` comes from `crates/grokhub-app/build.rs`, which reads the branch, short SHA, and beta N from git at build time. A beta build is labeled `X.Y.Z-beta.N`, where N is the commit count since the newest stable `vX.Y.Z` tag (`git rev-list --count <tag>..HEAD`). Shallow clones without tags fall back to `beta.0` until you `git fetch --tags`. The Cargo version itself never changes for a beta label. A build made without git shows just `GrokHub 3.5.0`.

Limits: building beta from a clone is Linux-only (`scripts/install-windows.ps1` has no `-Channel`); Windows gets Beta from the signed pre-releases. Beta turns itself off when beta catches up to main only on a Linux clone, because that check reads the clone's branches; elsewhere, turn it off in Labs. The Update chip still only notices new stable releases, so on beta, use Settings → **Update** to take the newest beta build.

## Pulse

**Pulse** (it was Ideas) is one stream in a single centered column: your front page for what changed in your games, PC and mods, what your watches found, and what the cabin can do for you next. Ideas and feed posts (daily drops, automation runs, news) share one list: an idea, then two posts, then the next idea, and so on. Ideas keep their rank order (up to four of the most useful first, then Games, PC, Mods & builds, Deals, Automations, and More for you; ideas saved under the old groups move over on their own). **Suggest for you** and **Feed instructions** sit on the right of the Pulse title. A small line under the header counts the posts; **Details** opens the last source check note. A post shows the source, the headline, two or three sentences, the source's own image when it has one, a plain-words line on why it is there ("You play Helldivers 2", "From r/buildapc, a source you follow", "Matches your interest in Rust"), and its chips. Each idea row has a category icon, a bold line, a short reason, and a ··· menu. Hover or arrow onto a row to see its chips inline; R, S, Enter, N, and D still act on the focused row (run, snooze, open, Not this, dismiss). Titles are the model's own "I can …" line, up to 70 characters. Images come only from the post's thumbnail or the linked page's `og:image`, are cached in `pulse-images/` in the config folder, and show a placeholder until they arrive.

The feed opens with **today's set**: posts from the last day, newest first, at most two from one game or source and twelve in all; older posts follow. Fetched and written posts leave the feed three days after they were posted unless you liked, saved, pinned or edited them. News for Steam games you play posts even when the game is not one of your interests. Idea runs read the games you play lately, the topics you follow and your newest open PC health findings, so ideas are about your own setup; game ideas stay read-only and allowed-data only.

Every card is one of five kinds: **Do** (one tap), **Watch** (news and results), **Learn** ("I can learn this and do it your way"), **Automate** (a repeat that could run on a schedule), and **Quiet** (kept, but not shown). Plain rules rank them, not the model: a skill ask, something due within a day, unfinished work on the same topic, and a repeat move a card up; a like or a use moves that topic up, an accepted card more; Not this pushes that topic well down. A card you scroll past only lowers its topic a little and never quiets it: a topic goes quiet only after Not this, and comes back on its own after 14 days. The model only writes the sentence. The ··· menu has **Run in the background** (sends the idea as `/bg`, so it runs invisibly like any background task; Ask mode refuses it, as it refuses every `/bg`), **Snooze until 9 AM**, **Always do this** (or **That's right** / **That's wrong** on a Learn card), **Open**, **Not this**, and **Dismiss**. Likes, Not this, Dismiss and right/wrong each add one line to `MEMORY.md`, for example `- [2026-10-04] pulse: dismissed "Sort the photos" reason=not-this`, and the next ranking reads them.

**Card reports and chips.** Every card carries a report: a title that says what was found ("bluetoothd crashed 4 times today"; a failing automation's card names the automation, how many runs failed and the last error), a two or three sentence summary, and the full background (what was checked, the evidence, why it matters) that opens under **Show the full report**. A card with no report falls back to a cleaned title, never a raw prompt. The quiet-hours digest keeps each update's own line and opens each one. Under each card sit up to four chips: the card's fixes (up to two, named for what they do, like "Look into the crashes" or "Find out why"; a card with no fixes shows its main action instead), **Discuss** when there is room, **Ignore for now**, and **Remind me later**. Ignore for now hides the card without teaching Pulse to show less of it. Remind me later brings it back tonight, half an hour before you usually wind down (quiet hours start, or what rhythm learned), when there is at least an hour left; otherwise when you next sit down (your usual start, 9 AM until it is learned). Like moved into ···.

**Card chat.** Discuss and every fix chip that needs a conversation open that card's own chat, never the chat that happens to be open, and its first message carries the whole report so the first reply already knows what the card found. In that chat a short "check into it" means the card's subject, and a program that keeps crashing gets the PC repair playbook. A crash card's "Look into the crashes" reads that program's crash history by the name on the card (its crash dumps and recent warnings on Linux, its Application log crashes on Windows): metadata only, never the dump, and it changes nothing.

**How a fix runs.** Nothing applies until you tap it. A read-only check or one quick reversible step runs quietly and leaves a dated receipt on the card. A fix that changes your computer opens a live checklist: each step done, running, waiting for your OK, not started, didn't work or didn't run, then the re-check, with **Stop fix** while it runs and **Undo fix** at the end. Settings > Pulse > **Fixes Loadout may apply on its own** has one switch per kind of fix, all off; a switch only skips the tap, and anything that changes your computer still asks on its approval card. The first switch covers a crash card's read-only crash history check.

**Fans, drivers, clocks.** Fans: on Linux the fix saves every fan's setting first, sets full speed in one step you approve with your password, checks the fans read full speed, and Undo fix puts each fan back with its own step. Under CoolerControl the card points you to CoolerControl; on Windows only your PC maker's own app is used. Drivers: the update list must name a newer GPU driver or firmware package, and the installed and repo versions are read again just before the fix and must match; any mismatch and nothing runs. A driver update runs only with a way back (a system snapshot, or the old package still in pacman's cache or offered by apt), and Undo puts the old driver back. On Arch the update is a full system update from the package lists already on disk; on Windows the card points to the GPU maker's own app or Windows Update. Clock speeds, power limits and undervolts are never changed, and no fan driver that anti-cheats flag (WinRing0, PawnIO, InpOut) is installed: those steps are refused outright. No fan or driver change runs while a game is running. The PC health sheet's footer says the same: "Changes fans only with a backup you can restore. Updates drivers only from the official source after checking it twice. Never touches clock speeds or a running game."

In the shell app, Pulse cards show the same title, summary, full report and chips, and Discuss or a fix chip opens the card's own chat with the report. The shell only reads: a fix chip puts the fix into that chat, and nothing runs until you send it.

**Feed instructions** is a plain-text prompt that shapes every future post, the summaries on posts fetched from your sources included. Edit it any time. After three likes or skips the cabin rewrites it itself, keeping your words and adding what it learned under "Show more of" and "Show less of". Pulse notifications go through one gate: only time-sensitive ones (due within the hour) pop up, never while a game is running or in quiet hours, and at most three a day; the rest wait on the page. In the shell app, Pulse posts also say where they are from and why, **Read it** opens the source, Love pressed again takes the heart off, today's set ends with "That's all for today", the page looks for new posts once a minute while it is open, and an empty feed says what the writer found last time with an **Add interests** button. Cards that arrive during quiet hours wait and come back as one "While you were in quiet hours" post. The Home and For You (formerly Ideas) data from older builds moves into Pulse once on first launch; nothing is deleted. The empty main chat does not show a Home card deck; cards live in Pulse. Once a day at your usual active hour (or on first open when rhythm has not learned yet), a **Start my day** Digest pulls together pick-up-where-you-left-off, watcher alerts, game news/sales, and one suggested next step from signals the cabin already holds — empty sections stay hidden, each line has a one-tap, and **Not today** dismisses the whole brief.

Once a week, at your usual active hour (or the Pulse brief hour you picked), Pulse posts a **Your week** recap Digest built only from opt-in counters already on the machine — games from library playtime, projects from code resume, prints and disk freed when those ledgers exist, top Loadout tasks, and one next-week suggestion. Sections with a signal turned off stay hidden. The share image written beside it never includes personal paths.

## Objectives and XP

**Objectives** holds the player's own goals ("99 fishing in osrs", "finish Elden Ring", "win 10 ranked matches"), kept in `objectives.json` and shared by the desktop app, the shell, web and phone. A goal typed in plain words is matched to a game in the player's own library, starts where they really are and has one target. The page has three parts. **Today** shows the goal closest to done, a "Pick up Elden Ring tonight?" line for one left a week, and on Mondays **Your week**: up to three real changes from last week (a level reached, goals done, the goal that moved most, weeks in a row) and one suggested goal to Track. **My goals** has Add, +1 for step goals, Done and Drop, and the suggested tray with Track and Not now (Not now hides one for 30 days). **This season** (a calendar quarter) counts goals done, shows the trophy shelf, and says how many goals are left for the season's badge; three done earn it.

Goals come from chat too. When a reply is about a game, the model may add a hidden `GAME_GOAL:` or `GAME_PROGRESS:` line. A goal the player asked to track is tracked at once; any other becomes one Track goal / Not now ask under the reply, at most once a chat. Progress from chat moves a bar only when the player's own message says the number, so a model's guess never does. Progress also comes from game data the player already allowed: the opt-in Steam achievements counts and saved Old School RuneScape hiscores reads. Nothing here talks to a game, its process or the network, so it can't touch anti-cheat. A goal moved that way shows **Checked**.

A tracked goal left three days gets a gentle follow-up: "Want to pick a night for your next Elden Ring session?". At most one per goal a week and two a week in all, never while a game is running, and the words never say how long it has been. After two go by with no progress, the last one says "I'll stop asking about Elden Ring, just say the word." Any progress starts it over. The desktop app sends it as a one-tap card through the proactive engine (budget, quiet hours and Not this apply); the shell shows it on Home and Objectives with **Plan it**, which puts the ask in the chat box.

**XP** is worked out from what the player already did, one line per thing in `xp-ledger.json`: 100 per finished task, 25 per checked step, 25 per Home card run and 50 when its work finishes, 10 per active day, and from goals 50 at each quarter of the way and 200 when one is done (300 for finishing a game or a skill to 99). The first goal done each season pays a one-time bonus. The ledger is rebuilt from the logs and goals each time it is read, so it can't drift and never goes down on its own. Past 150 a day, card and active-day XP counts half. Level 2 needs 200, each level after 50 more, up to 500 a level. Weeks run Monday to Sunday on local time: a week with any XP keeps the run going, two freezes cover missed weeks, and meeting the week's active-day target pays 100 or more. The target tunes itself, so there is nothing to set. Home's Objectives module opens the page.

## Personalities

**Settings → Personality** sets the voice every chat starts in; a chat can pick its own from its header. Every voice talks with the user like an adult friend: most subjects are fine, mature ones included, it can match their swearing, and it turns sincere for grief, health or real distress. Tone only: approvals, warnings and facts stay plain. Built-in voices removed from the list keep working: a chat set to Lawyer-precise speaks as Concise Pro, one set to Friendly Neighbor as Nyx.

**Dynamic chat** (on by default) lets another voice step in while the topic calls for it, like Chief Engineer for a build error or Gentle Listener when someone is venting, then hand back. It switches only after two turns that point the same way and stays at least three, except that a low mood moves to a support voice at once. A voice picked for a chat, or "talk like a pirate", holds it in place, background runs never switch, and an explicit voice is never picked this way. While a guest voice speaks, the personality pill and Nyx's card show it, and the switch sheet offers **Keep** to make it the chat's own.

**Adults-only personalities** is the one 18+ switch, off by default. The first time it turns on, a one-time check asks the user to confirm they are 18 or older and lists what changes. With it on, every voice can tell crude, raunchy jokes at the **Heat** the user picks (Cheeky, Spicy or Filthy), and the explicit presets show up. Jokes, never sex chat, outside the explicit presets; never about minors, real people or non-consent, and no slurs. Spicy and Filthy chats route as 18+, so they only go to xAI or the local model. "Roast me harder" and "ease off" move the heat for that chat inside the dial. A voice drops an unasked quip at most every four to six turns (three at Filthy), answer first, never on a frustrated, serious or repair turn, and backs off when quips get ignored; the quip bank in `crates/grokhub-core/assets/quips.toml` holds style examples the voice riffs on, not lines to paste.

## Background tasks

Work can run beside the chat while you keep talking. `/bg <task>` starts a separate native engine session that forks this chat's session, so it knows the conversation without writing into it. A bare `/bg` moves the live reply off the composer; it keeps going and its answer posts on that chat when it ends. Sending in another chat does the same to a reply that is still running there instead of cutting it off. Grok can start one itself with a `BACKGROUND_TASK: <instructions>` line in its reply. Up to 3 run at once. Each shows above the composer with its time, last tool, and Stop; `/bg stop` stops them all, and tray Halt or Ctrl+Alt+H stops them with the live turn (composer Stop and `/stop` leave them running). A result waits while its chat is mid-reply, and the next turn on that chat is told what came back. With Ask on, `/bg` and Grok's `BACKGROUND_TASK:` lines are refused, because a background run can't ask for approval (switch to Auto). Unwatched runs under Ask (background, automations, night, `/send`) fail closed: the native gate refuses shell, edit, write, and desktop tools, because nobody can answer a card. They end when the cabin quits.

## Code tab

The **Code** tab works on the project folder. The cabin and the desktop shell (`src-tauri/`) share its logic (`crates/grokhub-code`), the remembered commands, the secrets and the activity log, so a command confirmed in one is remembered in the other. Phones and the web app have no Code tab.

**Projects (desktop shell).** The bar at the top of the tab names the open project and its folder. **Switch project** lists the projects in `projects.json` (the list the cabin and `/project` use); **Open folder…** opens the system folder picker and adds the folder to the list; **New project** makes a folder in the work folder. Opening a project is the same as `/project bind`: the whole app works in that folder from then on, Chat included, and the tab reads everything again from it. A switch ends the terminal's shell, and is refused while a test run or deploy is still going. **Sessions** lists the saved chats that ran in the open project, newest first. A row opens that session in the agent window, and **New session** starts a new one there. A folder that is open but not in the list shows **Add to projects**.

**Agent window (desktop shell).** The right side of the tab is a conversation with the agent, with the same composer, cards, slash commands and Stop as Chat. It starts on a new session each time the app starts, and it keeps running while another tab shows. **Ask the agent to review** puts its prompt in a new session there. A session works in the folder of the project that was open when the agent window first showed it, named under the title as **Works in**; it keeps that folder for every later message, even when the app opens another project meanwhile. While a reply runs, the project bar holds the project and the other sessions. When the app's folder changes and no reply is running, the agent window starts a new session in the new folder. A conversation is open in one place at a time: a session the Chat tab has open is shown there, and a chat the agent window has open is shown on the Code tab when History, the bell or the Activity dock opens it. The agent window's session is never the chat that the Chat tab reopens at the next launch. Side answers, `/send`, `/bg` and `/consult` typed in a session use that session's folder. `/project bind` typed there moves the app as usual, and the agent window then starts a new session in the new folder. **Tasks**, under the conversation, lists that session's to-dos and helpers. In a session with a lead it updates when a task, helper or command changes, and it reads again every 15 seconds in case a change was missed; in any other session it reads every 2 seconds. Both read only while the tab shows. A running helper has **Stop**.

**The lead (desktop shell).** A session that starts in the agent window has a lead: it plans first, then hands the work to helpers. A saved chat from the Chat tab that is opened in the agent window is not such a session and works as it does in Chat. Until the first plan of a lead session is approved, every message there is read-only, `/chat` and `/queue` included; a side answer stays a side answer. The plan shows as a card with the plan in a text box. Edit the text and press **Approve plan** to approve it as edited, or write what should change and press **Ask for changes** to send it back. Nothing in the project changes before **Approve plan**. The plan is saved with the session as `sessions/<id>/plan.md` in the config folder, with your edits, and is removed with the session; `/view-plan` in the agent window shows the saved text. After the approval the lead writes one task per line of the plan's **Tasks** list and gives each task to a helper, and it checks each result before it closes the task. Tasks that change different files can run together: up to three writing helpers at once, each in a git worktree of its own. Tasks that change the same files run one after another, and in a folder that is not a git repository one writing helper runs at a time. Later messages in the session are read like any chat message, and the lead plans again for new work that is more than a small change. **Tasks** shows each task first, with its state and its helper (for example `Running · helper s2`): **Planned**, **Running**, **Needs you** (a running task while the session waits on your answer), **Review** (the helper finished and the lead has not closed the task), **Not merged** (its helper's work waits in a worktree, see **Helper work**; this comes before **Done**, whatever the lead set), **Done**, and **Failed** (the helper was stopped, or the lead cancelled the task). Helpers and commands are listed under them. A helper's task and its own row show its progress on a second line: the count and name of its last tool step, the tokens it has used, and how long it has run (for example `Step 3: read_file · 1.2k tokens · 2m 5s`). The time is as of the panel's last update and stops when the helper ends. **Details** on a helper's row opens a window with its last 40 steps, by tool name, and its result so far as plain text; **Close** or Esc closes it. Opening it takes nothing from the lead, which still gets the result. A task is matched to its helper by the task id at the start of the helper's title, so a task whose helper was started without it names no helper and shows only **Planned**, **Running**, **Done** or **Failed** from its own status. The approval changes the tools the session may use, so the first request after it re-reads the conversation without the prompt cache; the lead keeps the planning phase small by reading through explore helpers.

**Helper work (desktop shell).** A helper that runs in a worktree changes nothing in the project folder. When it ends, the app seals what it changed and lists it under **Helper work** in **Tasks**, also after a restart. Nothing goes into the project until you press **Merge**, or say yes when the lead asks to merge. The lead's request asks every time, also under Always and Auto; its card says how many files go into which folder and has only **Allow once** and **Deny**. It is refused in a read-only session and when nobody is there to answer, and the lead is told at once, with no card, when the work is not its to merge (partial, held, already merged or discarded). Merged files are uncommitted changes in the project folder: the app never commits, stages, or switches your branch. A helper's own row says what became of its work: `Ready to merge · 3 files`, `Partial · 3 files kept`, `No changes`, `Merged · 3 files`, `Conflict · a.rs, b.rs`, `Held · <why>` or `Discarded`. A row of the list shows the title, the same line (for a helper that did not finish it reads `Held · the helper did not finish`), `Partial · <how it ended>` when the helper did not finish, the counts (`1 new, 2 changed, 0 deleted`), the first five files, any files a merge left as you had changed them, and the worktree folder. Ignored files a helper wrote (build output, `.env.local`) are never merged; the row names them, and they stay in the worktree until you delete it.

- **Merge** merges work that is ready. A merge is worked out before any file is written, so a conflict changes nothing in the project and never writes conflict markers: the row turns to **Conflict** with the file names and offers **Merge again**, for after you changed the project.
- **Merge partial work** is for a helper that was stopped, failed or ran out of steps, one that changed its worktree's git state, and a worktree that changed after the helper ended. It asks first, with the counts. For a helper the app closed under, the first press only reads what it changed; the second asks.
- **Finish merge** and **Put files back** show when a merge stopped part way, for example because the app closed. Finish writes the files it had not written; Put files back restores the ones it had. Either leaves a file you changed meanwhile as it is and names it on the row. Until one of them is done the row has no Merge and no Discard.
- **Discard** deletes unmerged work and its worktree, after a confirm. It can't be undone.
- **Delete worktree** shows on merged work whose worktree was kept for its ignored files, and deletes that folder after a confirm.

A press that is refused shows the reason on its row and changes nothing. One merge runs at a time, and a merge is refused while the project is in the middle of a merge or rebase of your own, or has unresolved conflicts. The buttons are in the desktop app only: a paired browser lists the work without them.

**What it does.** It shows the branch, the changed files and one file's diff, and the built-in skills with what overrides them, all read only. It runs the project's test command and, once you turn it on for the project, a deploy command. It makes a branch, pushes it and opens a pull request. It has an editor for text files in the project and a terminal with your own shell, started in the project folder. It keeps the project's deploy secrets: the names in `code-secrets.json` in the config folder, the values in the system keychain, never shown again after you save them.

**What it asks.** The first run of a test command shows the exact command and asks; after a yes, the same command runs without asking in that project until you change it or press Forget. A deploy is off until you turn it on. In Ask mode (the default) every deploy, push and pull request shows its command and asks. In Auto-beta, a deploy you confirmed once runs without asking until its command changes, and a push or pull request skips the ask only for a branch made in the Code tab, on GitHub, into the PR base (`beta` unless changed). The cabin reads the mode, the PR base and the protected branches from the desktop shell's Settings → Code (`codeShip` in `shell.json`); with none saved it uses Ask. Deleting a secret asks first. A yes counts only for the command on the card: if the branch changed since, nothing runs. Making a branch, saving a file and opening the terminal don't ask.

**What it refuses, in either mode.** It never pushes `main`, the repo's default branch (read from the local `origin/HEAD`) or a branch you marked protected. It never force-pushes and never deletes a branch: the app builds every git and gh argument itself and passes no force, mirror, delete or prune flag. It doesn't push from a detached HEAD, without an `origin` remote, or to a host other than GitHub unless that is turned on, and a pull request opens on GitHub only. The editor opens and saves only inside the project: a path with `..`, a link that leads out or whose target is missing, anything in `.git`, a file over 512 KB or one that isn't UTF-8 text is refused, and so is a save after the project folder changed. A secret name that changes how programs run (`PATH`, `HOME`, `SHELL`, `TERM`, `GIT_TERMINAL_PROMPT`, anything starting `LD_` or `DYLD_`) is refused. Only one test run or deploy runs at a time.

**Good to know.** The app's own push does not run the repo's git hooks, so a `pre-push` hook is passed over; a rejected push is reported and never retried. A deploy gets the project's secrets as environment variables; test runs and the terminal do not. Test and deploy output and the Activity list show a secret value as `[redacted]`, along with key-shaped tokens. The terminal hides the secret values that were saved when it opened (one saved later is hidden after you close and open it again) and key-shaped tokens in what the shell prints; a value that reaches the screen a piece at a time, like one you type by hand, is not hidden. Commands typed in the terminal, `git push` included, are not checked by the push guard, and the tab says so. In the cabin, leaving the tab or switching projects ends the shell, and quitting the cabin ends a test run or deploy that is still going. The Code tab, in the cabin and in the desktop shell, has a Stop button beside a running test or deploy, which ends the run and everything it started. Activity (`code-activity.jsonl` in the config folder) keeps one line per push, pull request, new branch, blocked attempt, deploy, secret change (the name only), editor save (path and size) and terminal opening or closing, never what was typed or shown; test runs are not in it.

## Packaging

| Path | Role |
|------|------|
| `~/.local/bin/grokhub` | User install (`./scripts/install.sh --user`) |
| `/usr/bin/grokhub` | System / makepkg |
| `~/.config/GrokHub` | Linux user data (`app.json`, `projects.json`, `secrets.json`, memory) |
| `%LOCALAPPDATA%\Programs\GrokHub` | Windows cabin (`grokhub.exe`) |
| `%APPDATA%\GrokHub` | Windows user data |

Linux tarball: `grokhub-linux-v*.tar.gz` from `./scripts/make-release-bundle.sh`.  
Windows installer: `GrokHub-Setup-<version>.exe` from `./scripts/make-windows-release.ps1` (Inno Setup). A `vX.Y.Z` tag publishes both as a release; each push to `beta`, the nightly beta build and a `vX.Y.Z-beta.N` tag publish them as a pre-release named `v<version>-beta.<N>`, as described under the two channels above. On tags, when SignPath secrets are configured, the Setup and portable zip are Authenticode-signed (certificate by SignPath Foundation); see [CODE_SIGNING.md](CODE_SIGNING.md).

Every release and pre-release also carries `SHA256SUMS` (the SHA-256 of each file) and `SHA256SUMS.minisig`, a [minisign](https://jedisct1.github.io/minisign/) signature of it. The public key is [`packaging/minisign.pub`](../packaging/minisign.pub); the private key exists only as the `MINISIGN_SECRET_KEY` Actions secret. To check a download by hand:

```bash
minisign -V -p packaging/minisign.pub -m SHA256SUMS
sha256sum -c SHA256SUMS --ignore-missing
```

Setting up the key (owner, once): `minisign -G -W -p minisign.pub -s minisign.key` makes an unencrypted pair (the secret store is its protection; CI can't type a password). Paste all of `minisign.key` into the repo's `MINISIGN_SECRET_KEY` secret, commit `minisign.pub` as `packaging/minisign.pub`, then delete `minisign.key` or keep it offline. Without the secret, releases ship `SHA256SUMS` unsigned with a warning, and the updater refuses them.

Arch notes: [`packaging/README-ARCH.md`](../packaging/README-ARCH.md).
