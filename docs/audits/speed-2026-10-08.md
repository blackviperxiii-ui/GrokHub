# Speed audit: auto router and agentic harness (2026-10-08)

Base: `beta` @ `7afcebd4` (2.10.96). Prompt 28, phase 1: measure only, no behavior change.

## How it was measured

- **Speed spans** (`crates/grokhub-agent/src/timing.rs`): in memory, the newest 1,024 durations per span name, no disk write on the hot path. `route::live::decide` also writes its own per-step breakdown on the call's route record (`timing_us` in `spans/model-calls.jsonl`), so a real cabin's log shows where a slow send went.
- **Spans** cover `Router::choose` and every read inside `decide` (registry and profile snapshot, week budget, difficulty, accuracy-guard overrides, VerifyGate counts, self-tuning, the ladder with DE2 routine lookup, routing table, premium grants, provider key and grant check, budget notes), the route record and its span and health writes, `harness::decide`, `decide_harness`, the gate, the consent ledger load, the egress and provider guards, sealed reads and appends, keyring reads and writes, registry refresh, onboarding probes and table rebuilds, and on the send path: Enter to request, Enter to first token, request build to first token, and the agent loop's gap between steps, tool gate and tool run.
- **Bench** (`crates/grokhub-agent/src/route/speed_bench_tests.rs`): a config folder shaped like a few weeks of use (sealed consent ledger with 31 grants, 3,000 sealed egress lines, about 4 MB of model-call log with 5,000 route records, 2,000 spans in the chat's own file, 300 task outcomes, a provider with a key and a grant). Each iteration runs a chat turn, a 5-step agent task (`run_loop`, 4 tool calls then an answer), a 5-step desktop episode (`route::call_model`, the episode kernel's path) and a Grok Build turn (`route_gb_turn`), all with a stub model that runs the same egress guard XaiClient runs. Caches are warmed first, as a running cabin's would be.

```sh
cargo test -p grokhub-agent --release --lib speed_bench -- --ignored --nocapture --test-threads=1
```

A smoke test (`the_bench_records_every_hot_path_span`) runs the same bench for two iterations in CI and checks every span is recorded the expected number of times.

## Top time sinks, ranked

1. **DE2 routine lookup re-parses the model-call log on every new user message.** `learn::routine_for` (`route/learn.rs` ~260) reads `outcomes.jsonl` and, when any outcome shares the task's topic, the last 4,000 lines of `spans/model-calls.jsonl` (up to 4 MB) and parses each as a full span. `decide` calls it whenever a turn is new (`route/live.rs`, the ladder block), so every typed message, every Grok Build turn and every desktop step whose text changes pays it: about **28 ms p50 and 40 ms p95** with a 4 MB log, all before the request leaves. It is the whole of Enter to request.
2. **Grok Build turns route on the UI thread.** `route_gb_turn` is called from `kick_model` (`grokhub-app/src/app/chat_kick.rs` ~359 and ~401), so sink 1 is also a frame hitch of about 28 ms on every Grok Build send.
3. **The week's spend re-parses up to 20,000 log lines once a minute, under a lock.** `budget::load_week` (`route/budget.rs` ~304) caches per minute, but the first send after the minute turns re-reads the log tail (**28 ms p50, 37 ms p95**) while holding the `WEEK` lock, so a send can also wait on the cabin's own background budget tick.
4. **VerifyGate counts re-read the chat's span file twice per routed step in an episode.** `verify_counts` (in `decide`) and the verdict in `route_record` each parse the last 2,000 spans of `spans/<chat>.jsonl` (`route/signals.rs` ~83): about **4 ms p95 each, 8 ms per desktop or episode step**.
5. Small, per send, and fine as they are: the egress guard (about 0.1 ms: one sealed consent read and one sealed egress append), the provider key and grant check (0.08 ms, the key answer is cached), the consent load (0.06 ms). The agent loop's own work between steps is about 0.1 ms p50 (`loop:step_gap` minus the tool itself).

## Checked and not a sink

- `harness::decide` and the gate are pure (0 to 2 µs p95); guards are cheap and stay as they are.
- Keyring: the key is unlocked once and held (`at_rest` caches it, rechecking every `RECHECK`); reads are 3 µs.
- Registry refresh, onboarding probes and table rebuilds already run on a background thread (`router_ui.rs`), never on the send path.
- Difficulty is a heuristic on the hot path; the on-device model scoring path is off (R3a flag) and stays off.
- Effort: chat starts at Medium and drops to Low for short asks (`d < 0.3`); before R1 the default was High, so the router does not make replies slower by thinking harder.
- Shadow and canary marks are computed in memory next to the pick (under 1 µs).

## Not measured here

- The network and the model itself (the stub answers at once). Whether Auto switching models between turns costs prompt-cache hits needs real route records (`cached` vs `input` tokens per episode); the bench can't show it.
- The auto-review judge (a model call per tool step in Auto mode) is a safety check and is out of scope for speed changes.
- Windows disk timing: the bench runs on Linux; CI runs the smoke test on both.

## Plan for PR B

1. Follow the model-call log and the chat span files incrementally: keep the parsed tail in memory and read only the bytes appended since the last read (re-read in full when a file shrinks or is replaced). Fixes sinks 1, 3 and 4 with the same records the code reads today.
2. Don't hold the `WEEK` lock while reading.
3. Add budget tests: a `decide` call and a `harness::decide` call on the bench fixture must stay under a time budget set from these numbers with headroom.
